# ขั้น 6 — Playwright test ตาม user flow

ถ้า prototype ของ Activity ที่ระบุยังไม่มี Playwright test ตาม user flow ให้สร้าง test ที่เดินหน้าจอตามลำดับใน flow ตรวจรายละเอียดหน้าจอ (Extracting screen details) และเก็บ screenshot ทุกหน้าจอ แล้วรันจนผ่านทั้งหมด

Activity: **{Activity}**

## ขอบเขต
- **ห้ามแตะไฟล์ Excel ใด ๆ**
- prototype = โค้ดใน `input/code/` หรือ repo ที่ไฟล์ใน `input/code/` ชี้ไป — ถ้า `input/code/` ว่าง หรือขั้น 3 ถูกข้าม ให้แจ้ง "ข้ามขั้น 6 — ไม่มี prototype" แล้วไปสรุปท้ายงาน
- **ห้ามแก้โค้ดของ prototype** (หน้าจอ, logic, style, mock data, `data-testid`) — เขียนได้เฉพาะไฟล์ test และไฟล์ตั้งค่า test ตามข้อ 5 และต้องผ่านจุดตรวจ 3 ก่อน
- ถ้า test ไม่ผ่านเพราะ prototype ขาดหน้าจอ/ปุ่ม/สถานะตาม flow → **ห้ามแก้ prototype** ให้บันทึกเป็นจุดที่ prototype ไม่ตรง flow (ข้อ 7)
- ต้องมี `work/extract/A{เลข 2 หลัก}_extract.md` (และ `_verify.md` ถ้าไม่ได้ข้ามขั้น 3) ก่อน

## ขั้นตอน

### 1. ตรวจว่ามี test ตาม user flow แล้วหรือยัง
- หา `playwright.config.*` และไฟล์ `*.spec.ts` / `*.spec.js` (ไม่นับ `node_modules`) ใน prototype
- ถ้ามีแผนที่โค้ด (`work/graph/graphify-out/graph.json`) ใช้ `graphify query` ตาม `code-graph.md` ข้อ 3 ช่วยหา route, หน้าจอตาม Page Code, กลไกตั้งสถานะเริ่มต้น (mock state / seed / login) และ test ที่มีอยู่ — แล้วเปิดไฟล์จริงเพื่อยืนยัน ถ้ายังไม่มีแผนที่ (เช่น สั่ง `/ecmis <เลข> test`) ให้สร้างตาม `code-graph.md` ข้อ 2 ก่อน
- จับคู่ test ที่มีอยู่กับ flow ของ Activity นี้ จากชื่อไฟล์ ชื่อ `describe`/`test` และ comment หัวไฟล์ (Flow ID, Screen Seq ID, Page Code, LAW / Function No., Test Case ID)
- ผล:
  - ทุก flow มี test แล้ว → แจ้ง "prototype มี Playwright test ตาม user flow ครบแล้ว" แสดงตาราง flow ↔ ไฟล์ test แล้วไปสรุปท้ายงาน
  - มีบางส่วน → ทำต่อเฉพาะ flow ที่ยังไม่มี test
  - ไฟล์ที่ขั้น 6 เคยสร้าง (มี comment หัวไฟล์ `generated by /ecmis ขั้น 6`) → อัปเดตไฟล์เดิม ไม่สร้างซ้ำ

### 2. รวบรวม user flow
แหล่งหลักคือ **เอกสาร/ไฟล์ user flow ในตัว prototype** เรียงตามลำดับนี้:
1. ไฟล์ flow ใน repo เช่น `*.drawio`, `FLOW_MATRIX.md`, `docs/`, `context/user-flow/`, `README.md`, `PRODUCT.md`, `QA_CHECKLIST.md`, `*testing-guide*`
2. `11 Screen Sequence` และ `14–15 Test Case / Test Steps` ในไฟล์ extract ของ Activity นี้ (ใช้เทียบ และใช้รหัส FLOW/SCR/TC เป็นชื่ออ้างอิง)

- `.drawio` เป็น XML — อ่านชื่อกล่องและลูกศรเพื่อเรียงลำดับหน้าจอและทางแยก (Forward / Return / Reject)
- ถ้าเอกสารใน prototype กับไฟล์ extract ไม่ตรงกัน ให้ยึดเอกสารใน prototype สำหรับการเดินหน้าจอ และบันทึกความต่างไว้ในรายงาน
- ถ้าไม่พบเอกสาร flow ใน prototype เลย ให้ใช้ Screen Sequence จากไฟล์ extract และแจ้งผู้ใช้ในจุดตรวจ 3
- **ห้ามเดา** flow ที่ไม่มีในเอกสาร — ถ้าไม่รู้ว่ากดอะไรต่อ ให้ยกไปเป็นคำถามในจุดตรวจ 3
- ต่อ flow ต้องได้: Flow ID, ชื่อ flow, ผู้ใช้/บทบาท, ลำดับหน้าจอ (Screen Seq ID, Page Code, ชื่อหน้าจอ), การกระทำที่พาไปหน้าจอถัดไป, ทางแยก Happy Path / Negative / Return-Rework และ Test Case ID ที่เกี่ยวข้อง

### 3. เตรียมการรัน prototype
ตรวจชนิด prototype แล้วเลือกวิธีเปิดสำหรับ `webServer` ใน config:

| ชนิด | สังเกตจาก | คำสั่งเปิด |
|---|---|---|
| Vite / React / Vue | `package.json` มี `vite` | `npx vite --port <PORT> --strictPort` (ใช้ `pnpm` ถ้ามี `pnpm-lock.yaml`) |
| Next / อื่น ๆ ที่มี script `dev` | `package.json` | script `dev` ของโปรเจกต์พร้อมกำหนดพอร์ต |
| HTML ล้วน | มีแต่ `.html` ไม่มี `package.json` ที่ root | `npx http-server <root> -p <PORT> -c-1 --silent` |
| Blazor / .NET | `*.csproj`, `*.sln` | `dotnet run --project <csproj> --urls http://127.0.0.1:<PORT>` |

- เลือกพอร์ตที่ไม่ชนกับ config เดิมของ repo
- ถ้า prototype ต้องใช้ฐานข้อมูล/บริการอื่น หรือเปิดไม่ขึ้น → แจ้งผู้ใช้ในจุดตรวจ 3 ว่าต้องเตรียมอะไร (ห้ามแก้ prototype เพื่อให้เปิดได้)
- การตั้งสถานะเริ่มต้น: ใช้กลไกที่ prototype มีอยู่แล้ว (mock state, localStorage seed, หน้า login/สลับบทบาท) — ห้ามเพิ่ม mock ใหม่ในโค้ด prototype

### 4. Extracting screen details
แจ้งความคืบหน้า `ขั้น 6/6 Extracting screen details… (หน้าจอ x/y)`
เปิด prototype จริงด้วย Playwright (สคริปต์ชั่วคราวใน scratchpad) เดินตาม flow จากข้อ 2 แล้วเก็บรายละเอียดของทุกหน้าจอ:
- URL / route, หัวข้อหน้าจอ
- ฟิลด์ (label, ชนิด, บังคับกรอกไหม), ปุ่ม/Action, สถานะ/ป้าย, ข้อความ validation/แจ้งเตือนที่เห็น
- selector ที่จะใช้ใน test โดยเลือกตามลำดับ: `data-testid` ที่มีอยู่แล้ว → `getByRole` + ชื่อ → `getByLabel` → `getByText` (ห้ามใช้ selector ที่ผูกกับ CSS class หรือตำแหน่ง nth ถ้าเลี่ยงได้)

บันทึกที่ `work/extract/A{เลข 2 หลัก}_screens.md` เป็นตารางต่อหน้าจอ: `Flow ID | Screen Seq ID | Page Code | ชื่อหน้าจอ | URL | หัวข้อ | ฟิลด์ | ปุ่ม | สถานะ/ข้อความ | selector | ที่มา (เอกสาร flow / extract / prototype path)`
หน้าจอที่ flow ระบุแต่หาใน prototype ไม่เจอ ให้ใส่ `— ไม่พบใน prototype —`

### 5. ⏸ จุดตรวจ 3 — ยืนยันก่อนเขียน test ลง prototype
แสดงในแชท (ภาษาง่าย ๆ):
1. ตาราง `| Flow | จำนวนหน้าจอ | Test Case (Happy / Negative / Return) | ไฟล์ test ที่จะสร้าง |`
2. แหล่ง user flow ที่ใช้ และความต่างกับไฟล์ extract (ถ้ามี)
3. หน้าจอ/การกระทำที่หาใน prototype ไม่เจอ และคำถามที่ยังไม่มีคำตอบ
4. ไฟล์ทั้งหมดที่จะเพิ่ม/แก้ใน prototype และสิ่งที่จะติดตั้ง (`@playwright/test`, browser Chromium)
5. สิ่งที่ผู้ใช้ต้องเตรียมเพื่อรัน prototype (ถ้ามี)

ถามผู้ใช้ด้วย AskUserQuestion: `สร้าง test เลย` / `ขอตอบคำถามก่อน` / `ข้ามขั้นนี้`
**ห้ามเขียนไฟล์ลง prototype ก่อนได้รับการยืนยัน**

### 6. เขียน test
ตำแหน่งไฟล์:
- prototype ที่มี `package.json` ที่ root → config ที่ root `playwright.config.ts` (ถ้ายังไม่มี), เพิ่ม `@playwright/test` ใน devDependencies และ script `"test:e2e": "playwright test"`, test อยู่ใน `e2e/`
- prototype HTML ล้วน / .NET → สร้างโฟลเดอร์ `e2e/` ที่มี `package.json`, `playwright.config.ts` และ test ของตัวเอง ไม่แตะไฟล์อื่นของ prototype
- ถ้ามี config/โฟลเดอร์ test อยู่แล้ว ให้ใช้ของเดิมและเขียนตาม style ของ test ที่มี

config (ตามแบบ prototype Activity 6): `testDir` ชี้โฟลเดอร์ test, `locale: 'th-TH'`, `timezoneId: 'Asia/Bangkok'`, `trace: 'on-first-retry'`, `screenshot: 'only-on-failure'`, project `chromium`, `webServer` ตามข้อ 3 พร้อม `reuseExistingServer: !process.env.CI`

โครงไฟล์:
```
e2e/
  helpers/screen.ts          ← ฟังก์ชัน checkScreen(): ตรวจรายละเอียดหน้าจอ + เก็บ screenshot
  flows/<flow-id>-<ชื่อสั้น>.spec.ts   ← 1 ไฟล์ต่อ 1 flow
  screenshots/<FLOW-ID>/<ลำดับ>-<SCR-ID>.png
```

กติกาการเขียน:
- comment หัวไฟล์: `generated by /ecmis ขั้น 6 — Activity {nn}`, Flow ID, ชื่อ flow, ลำดับหน้าจอ และแหล่ง user flow ที่ใช้ (ไฟล์ + หัวข้อ)
- `test.describe('<Flow ID> — <ชื่อ flow>')` และแต่ละ `test` ขึ้นต้นด้วย Test Case ID (ถ้ามี) เช่น `TC-A05-003 · Return/Rework — …`
- แยก `test` ตามเส้นทาง: Happy Path, Negative (เช่น ไม่กรอกช่องบังคับ แล้วต้องเห็น validation) และ Return/Rework ตามทุก Decision ของ flow
- **ทุกหน้าจอ** ห่อด้วย `test.step('<Screen Seq ID> · <ชื่อหน้าจอ>', …)` แล้วเรียก `checkScreen()` ซึ่ง:
  - ตรวจ URL/หัวข้อ และตรวจว่าฟิลด์ ปุ่ม สถานะ ตามข้อ 4 แสดงอยู่ (`toBeVisible` / `toContainText`)
  - เก็บ screenshot เต็มหน้าที่ `e2e/screenshots/<FLOW-ID>/<ลำดับ 2 หลัก>-<SCR-ID>.png` และแนบเข้า report ด้วย `testInfo.attach`
- หลังตรวจหน้าจอ ทำการกระทำตาม flow (กรอก, กด) เพื่อไปหน้าจอถัดไป แล้วตรวจผลที่ตามมา (หน้าจอถัดไป / สถานะ / ข้อความ)
- ข้อความภาษาไทยในการตรวจ ให้คัดลอกจากหน้าจอจริงตามข้อ 4 ห้ามพิมพ์เอง
- ห้ามใช้ `waitForTimeout` — ใช้ `expect(...)` / `expect.poll` รอสถานะแทน
- test ต้องอิสระต่อกัน (ตั้งสถานะเริ่มต้นใน `beforeEach`)
- เพิ่ม `e2e/screenshots/`, `test-results/`, `playwright-report/` ใน `.gitignore` ของ prototype ถ้ายังไม่มี (ถามไว้แล้วในจุดตรวจ 3)

### 7. ติดตั้งและรัน จนผ่านทั้งหมด
1. ติดตั้ง: `npm i -D @playwright/test` (หรือ `pnpm add -D` ตาม lockfile) แล้ว `npx playwright install chromium`
2. รัน `npx playwright test <โฟลเดอร์/ไฟล์ของ Activity นี้>`
3. test ไม่ผ่าน → ดูสาเหตุจาก error, trace, screenshot:
   - **ปัญหาที่ test** (selector ผิด, รอไม่พอ, ลำดับกดผิด, สถานะเริ่มต้นไม่ถูก) → แก้ test แล้วรันใหม่
   - **prototype ไม่ตรง flow** (ไม่มีหน้าจอ/ปุ่ม/สถานะที่เอกสารกำหนด หรือกดแล้วไปผิดหน้า) → ห้ามแก้ prototype ให้เปลี่ยน test นั้นเป็น `test.fixme(true, '<เหตุผล + ที่มาในเอกสาร flow>')` เฉพาะส่วนที่ติด และบันทึกลงรายการ "prototype ไม่ตรง flow"
   - รันไม่ได้เลย (prototype เปิดไม่ขึ้น, ติดตั้งไม่ได้) → หยุดแจ้งผู้ใช้พร้อม error
4. เมื่อผ่านแล้ว รันทั้งชุดซ้ำอีก 1 รอบด้วย `--repeat-each=2` เพื่อตรวจว่าไม่ flaky
5. **เกณฑ์เสร็จ:** failed = 0 และ flaky = 0 (fixme นับแยกและต้องมีเหตุผลทุกรายการ)
6. ถ้า repo มี test ชุดเดิมอยู่ ให้รันชุดเดิมด้วย และรายงานว่าผลไม่ต่างจากก่อนเพิ่ม test
