# Step 6 — Playwright tests per user flow

If the given Activity's prototype has no Playwright tests per user flow, create tests that walk the screens in flow order, verify screen details (Extracting screen details), take a screenshot of every screen, and run until all pass.

Activity: **{Activity}**

## Scope
- **Never touch any Excel file**
- prototype = code in `input/code/` or the repo a file in `input/code/` points to — if `input/code/` is empty or step 3 was skipped, say "ข้ามขั้น 6 — ไม่มี prototype" and go to the final summary
- **Never modify prototype code** (screens, logic, styles, mock data, `data-testid`) — only test files and test config files per item 5 may be written, and only after Checkpoint 3
- If a test fails because the prototype lacks a screen/button/status from the flow → **never fix the prototype**; record it as a prototype-vs-flow mismatch (item 7)
- `work/extract/A{2-digit no.}_extract.md` (and `_verify.md` unless step 3 was skipped) must exist first

## Procedure

### 1. Check whether user-flow tests already exist
- Look for `playwright.config.*` and `*.spec.ts` / `*.spec.js` files (excluding `node_modules`) in the prototype
- If a code map exists (`work/graph/graphify-out/graph.json`), use `graphify query` per `code-graph.md` item 3 to find routes, screens by Page Code, initial-state mechanisms (mock state / seed / login), and existing tests — then open the actual files to confirm. If there is no map yet (e.g. `/ecmis <no.> test`), build it per `code-graph.md` item 2 first
- Match existing tests to this Activity's flows by file name, `describe`/`test` names, and header comments (Flow ID, Screen Seq ID, Page Code, LAW / Function No., Test Case ID)
- Result:
  - Every flow has tests → say "prototype มี Playwright test ตาม user flow ครบแล้ว", show a flow ↔ test file table, and go to the final summary
  - Partial → continue only with flows lacking tests
  - Files previously created by step 6 (header comment `generated by /ecmis ขั้น 6`) → update them, don't duplicate

### 2. Gather the user flows
Primary source is **the user-flow documents/files inside the prototype**, in this priority:
1. Flow files in the repo, e.g. `*.drawio`, `FLOW_MATRIX.md`, `docs/`, `context/user-flow/`, `README.md`, `PRODUCT.md`, `QA_CHECKLIST.md`, `*testing-guide*`
2. `11 Screen Sequence` and `14–15 Test Case / Test Steps` in this Activity's extract file (for comparison, and use FLOW/SCR/TC IDs as reference names)

- `.drawio` is XML — read box labels and arrows to order screens and branches (Forward / Return / Reject)
- If prototype documents and the extract file disagree, follow the prototype documents for screen navigation and record the differences in the report
- If no flow documents exist in the prototype, use the extract file's Screen Sequence and tell the user at Checkpoint 3
- **Never guess** flows not in the documents — if the next action is unknown, raise it as a question at Checkpoint 3
- Per flow you need: Flow ID, flow name, user/role, screen order (Screen Seq ID, Page Code, screen name), the action leading to the next screen, Happy Path / Negative / Return-Rework branches, and related Test Case IDs

### 3. Prepare to run the prototype
Detect the prototype type and choose how to start it for `webServer` in the config:

| Type | Detected by | Start command |
|---|---|---|
| Vite / React / Vue | `package.json` has `vite` | `npx vite --port <PORT> --strictPort` (use `pnpm` if `pnpm-lock.yaml` exists) |
| Next / others with a `dev` script | `package.json` | the project's `dev` script with a port set |
| Plain HTML | only `.html`, no `package.json` at root | `npx http-server <root> -p <PORT> -c-1 --silent` |
| Blazor / .NET | `*.csproj`, `*.sln` | `dotnet run --project <csproj> --urls http://127.0.0.1:<PORT>` |

- Pick a port that doesn't clash with the repo's existing config
- If the prototype needs a database/other services or won't start → tell the user at Checkpoint 3 what to prepare (never modify the prototype to make it start)
- Initial state: use mechanisms the prototype already has (mock state, localStorage seed, login/role-switch page) — never add new mocks to prototype code

### 4. Extracting screen details
Report progress `ขั้น 6/6 Extracting screen details… (หน้าจอ x/y)`
Open the real prototype with Playwright (temporary script in scratchpad), walk the flows from item 2, and collect details of every screen:
- URL / route, screen heading
- Fields (label, type, required?), buttons/Actions, statuses/badges, visible validation/notification messages
- Selectors for tests, in this preference order: existing `data-testid` → `getByRole` + name → `getByLabel` → `getByText` (avoid selectors tied to CSS classes or nth position when possible)

Save to `work/extract/A{2-digit no.}_screens.md` as a per-screen table: `Flow ID | Screen Seq ID | Page Code | ชื่อหน้าจอ | URL | หัวข้อ | ฟิลด์ | ปุ่ม | สถานะ/ข้อความ | selector | ที่มา (เอกสาร flow / extract / prototype path)`
Screens in the flow that can't be found in the prototype → `— ไม่พบใน prototype —`

### 5. ⏸ Checkpoint 3 — confirm before writing tests into the prototype
Show in chat (plain Thai):
1. Table `| Flow | จำนวนหน้าจอ | Test Case (Happy / Negative / Return) | ไฟล์ test ที่จะสร้าง |`
2. User-flow sources used and differences from the extract file (if any)
3. Screens/actions not found in the prototype, and unanswered questions
4. All files to be added/modified in the prototype and what will be installed (`@playwright/test`, Chromium browser)
5. What the user must prepare to run the prototype (if anything)

Ask with AskUserQuestion: `สร้าง test เลย` / `ขอตอบคำถามก่อน` / `ข้ามขั้นนี้`
**Never write files into the prototype before confirmation**

### 6. Write the tests
File locations:
- Prototype with `package.json` at root → root `playwright.config.ts` (if missing), add `@playwright/test` to devDependencies and script `"test:e2e": "playwright test"`, tests in `e2e/`
- Plain HTML / .NET prototype → create an `e2e/` folder with its own `package.json`, `playwright.config.ts`, and tests; touch no other prototype files
- If a test config/folder already exists, reuse it and follow the existing test style

Config (modeled on the Activity 6 prototype): `testDir` pointing to the test folder, `locale: 'th-TH'`, `timezoneId: 'Asia/Bangkok'`, `trace: 'on-first-retry'`, `screenshot: 'only-on-failure'`, project `chromium`, `webServer` per item 3 with `reuseExistingServer: !process.env.CI`

Layout:
```
e2e/
  helpers/screen.ts          ← checkScreen(): verify screen details + take screenshot
  flows/<flow-id>-<short-name>.spec.ts   ← 1 file per flow
  screenshots/<FLOW-ID>/<order>-<SCR-ID>.png
```

Writing rules:
- Header comment: `generated by /ecmis ขั้น 6 — Activity {nn}`, Flow ID, flow name, screen order, and the user-flow source used (file + heading)
- `test.describe('<Flow ID> — <flow name>')`, and each `test` starts with the Test Case ID (if any), e.g. `TC-A05-003 · Return/Rework — …`
- Separate `test`s per path: Happy Path, Negative (e.g. leave a required field empty and expect validation), and Return/Rework for every Decision in the flow
- Wrap **every screen** in `test.step('<Screen Seq ID> · <screen name>', …)` and call `checkScreen()`, which:
  - Checks URL/heading and that the fields, buttons, statuses from item 4 are shown (`toBeVisible` / `toContainText`)
  - Saves a full-page screenshot to `e2e/screenshots/<FLOW-ID>/<2-digit order>-<SCR-ID>.png` and attaches it to the report via `testInfo.attach`
- After checking a screen, perform the flow action (fill, click) to reach the next screen, then assert the outcome (next screen / status / message)
- Thai text in assertions must be copied from the real screen per item 4 — never type it yourself
- Never use `waitForTimeout` — use `expect(...)` / `expect.poll` to wait for state
- Tests must be independent (set initial state in `beforeEach`)
- Add `e2e/screenshots/`, `test-results/`, `playwright-report/` to the prototype's `.gitignore` if missing (already asked at Checkpoint 3)

### 7. Install and run until all pass
1. Install: `npm i -D @playwright/test` (or `pnpm add -D` per lockfile), then `npx playwright install chromium`
2. Run `npx playwright test <this Activity's folder/files>`
3. Failing test → diagnose from error, trace, screenshot:
   - **Test problem** (wrong selector, insufficient wait, wrong click order, wrong initial state) → fix the test and rerun
   - **Prototype doesn't match the flow** (missing screen/button/status the documents require, or navigates to the wrong page) → never fix the prototype; change only the blocked part to `test.fixme(true, '<reason + source in flow document>')` and record it in the "prototype ไม่ตรง flow" list
   - Can't run at all (prototype won't start, install fails) → stop and tell the user with the error
4. Once passing, rerun the whole suite once with `--repeat-each=2` to check for flakiness
5. **Done when:** failed = 0 and flaky = 0 (fixme counted separately, each with a reason)
6. If the repo has an existing test suite, run it too and report that results are unchanged from before the new tests

### 8. Record and report
Save `work/extract/A{2-digit no.}_playwright.md`:
- Table `Flow ID | Test Case ID | ไฟล์ test | จำนวนหน้าจอ | ผล (ผ่าน / fixme)`
- Screenshot paths per flow
- "prototype ไม่ตรง flow" list: Flow / Screen Seq ID | สิ่งที่เอกสารกำหนด [ที่มา] | สิ่งที่ prototype ทำจริง [path] — suggest the user open these as Open Issues in the next `/ecmis` run
- Rerun command, e.g. `npx playwright test e2e/flows`

Brief report to the user (Thai): number of flows / screens / tests created, run result (ผ่าน / fixme), screenshot location, prototype-vs-flow mismatches, and how to run it themselves
